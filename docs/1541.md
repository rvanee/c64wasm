The 1541 is a computer of its own: a 6502 at 1 MHz, 2 KB of RAM, 16 KB of
DOS ROM and two 6522 VIAs. The emulator runs the real DOS ROM on the
shared 6502 core (see [cpu.md](cpu.md)), and models the hardware around
it: the serial interface, the read/write electronics and the mechanism.
Nothing in the C64 or the drive takes a shortcut through the protocol: a
`LOAD` is the KERNAL and the DOS talking over three wires, bit by bit, and
reading GCR bits from a turning disk.

Where community descriptions of the 1541 disagree, the question was
settled from the DOS ROM's own code (which addresses it touches, which
values it writes, which way it branches), and, for the serial interface,
from MAME's schematic-level model.

## Address map

| Range | What |
|---|---|
| `$0000-$07FF` | 2 KB RAM, mirrored up to `$17FF` |
| `$1800-$1BFF` | VIA1 (serial bus), 16 registers mirrored |
| `$1C00-$1FFF` | VIA2 (drive control), 16 registers mirrored |
| `$C000-$FFFF` | DOS ROM (16 KB) |
| elsewhere | open bus, reads `$FF` |

## Clock and power

The drive has its own 16 MHz crystal divided by 16: exactly 1 MHz,
independent of the C64's PAL or NTSC clock. The C64 runs it through a
`ClockBridge` once per C64 cycle (see
[architecture.md](architecture.md#two-clocks-clockbridge)). The drive
starts at the reset vector; the head is parked at track 1.

## One drive cycle: `LogicBoard::tick`

The 6502 calls `tick()` before each of its bus accesses. In order:

1. VIA1 and VIA2 count one cycle.
2. What the CPU last wrote to VIA2 is applied: PB2 to the motor, PB5-6 to
   the bit clock's density, PB0-1 to the stepper (a step resets the read
   framing), port A's pins to the write shift register, CB2 to read/write
   mode.
3. The mechanism counts a cycle; the read/write electronics run the bit
   cells that fall into this cycle.
4. The activity LED takes PB3.
5. The outputs go back to VIA2: the last byte read on port A, SYNC on PB7,
   write protect on PB4, byte ready on CA1. Byte ready also latches an
   edge for the CPU's SO pin.

So a byte completed in this cycle is already on port A when CA1 latches
it, and V is set in the same cycle, before the CPU's access completes. `tick()` never stalls
the CPU (nothing on the drive's bus steals cycles). The IRQ line is VIA1
OR VIA2.

## The serial interface (VIA1)

The C64 and the drives share ATN, CLOCK and DATA, open-collector lines
that anyone can pull low (`cbm_iec`). The 1541 has inverting drivers and
receivers, so on VIA1 port B a 1 on an output bit pulls the line low, and
an input bit reads 1 while the line is low:

| Bit | Signal |
|---|---|
| PB0 | DATA in |
| PB1 | DATA out |
| PB2 | CLOCK in |
| PB3 | CLOCK out |
| PB4 | ATNA (ATN acknowledge) |
| PB5-6 | device number pads |
| PB7 | ATN in |
| CA1 | ATN, rising edge (the DOS sets PCR = `$01` at `$EB2F` and enables it at `$EB37`) |

These were confirmed from the ROM: the ATN handler at `$E85B` sets PB4
first (`ORA #$10`) and then polls PB7 and PB2 in the order of the
protocol's handshake; the IRQ handler at `$FE67` tests VIA1 IFR bit 1 (CA1)
and calls the ATN handler at `$E853`.

**The ATN-acknowledge gate.** An XOR gate on the board (UD3, a 7486 into a
7406) pulls DATA low whenever ATN and ATNA differ:

```
DATA pulled low = DATA OUT || (ATN asserted XOR ATNA)
```

When the C64 asserts ATN, the drive answers by pulling DATA within
nanoseconds, in hardware, even while its CPU is busy. The DOS then sets
ATNA, which releases the gate, and from then on DATA OUT alone decides.
When ATN is released, DATA stays low until the DOS clears ATNA. The
KERNAL waits less than a millisecond for that answer (about 930 cycles,
at `$EEB3`); the DOS can take much longer to react, because it runs its
job loop inside the VIA2 timer interrupt with interrupts disabled.
Without the gate the KERNAL gave up on commands the drive hadn't answered
yet, and `LOAD` stalled. The model follows MAME's `c64h156`
(`m_atni ^ m_atna`). `serial_interface::bus_output(pb, atn)`
computes it; that is why a drive's output depends on the bus's ATN level.

**Device number.** Two solder pads pull PB5 and PB6 low. Both closed reads
0 and gives device 8; cut pads give 9, 10 or 11. The DOS reads them at
`$EB3A` and computes its talk address as `$48 + number`. `Drive1541::new`
takes 8-11 and sets the bits.

**Timing.** The bus is recomputed and presented to every drive once per C64
cycle, and ATN reaches VIA1's CA1 at the same time, asynchronous to the
drive's own clock.

## Read/write electronics (`read_write.rs`)

### Bit clock

The density bits (VIA2 PB5-6) select one of four bit rates. The DOS sets
them by track:

| Zone (PB6-5) | Tracks | Sectors | Bit rate | Bytes per track at 300 rpm |
|---|---|---|---|---:|
| `11` | 1-17 | 21 | 307,692 bit/s | 7,692 |
| `10` | 18-24 | 19 | 285,714 bit/s | 7,142 |
| `01` | 25-30 | 18 | 266,667 bit/s | 6,666 |
| `00` | 31-35 | 17 | 250,000 bit/s | 6,250 |

An integer accumulator adds the bit rate every 1 MHz cycle and runs one
bit cell per 1,000,000, so the cell timing is exact on average (3.25 to 4
cycles per bit) without drift. No cells run while the motor is off or no
disk is in the drive.

### Reading

Each bit cell reads the bit under the head:

- The bit shifts into an 8-bit shift register.
- A run of ten or more 1-bits is a **sync mark**: PB7 reads 0 while it
  passes, and the byte framing restarts, so the first byte after a sync
  is aligned to it. (GCR data never has more than eight 1-bits in a row, so
  ten can only be a sync mark.)
- After eight bits, the byte goes to VIA2 port A and **byte ready** fires
  for one cycle. It drives VIA2 CA1 (falling edge) and the 6502's SO pin
  (sets V), which the DOS's read loops test with `BVC *` / `CLV`.

A half-track without data still clocks the separator: it reads zeros,
never a sync, so byte ready keeps its pace and the DOS's "look for a sync"
loops time out as on a real drive with an unformatted track.

### Writing

With CB2 low the electronics write instead of read. Every byte time, the
value on VIA2 port A's pins is written over the 8 bit cells that byte
time spanned, and byte ready fires. The DOS answers each byte ready by
putting the next byte on port A. A value left there is written again
every byte time, which the formatter relies on: it writes `$FF` once and
counts 10,240 byte-ready pulses for a long sync (`$FDA3`), and does the
same with `$55` for the gaps (`$FB12`).

The value is committed when the byte time ends, as VICE does: the DOS
writes the last byte of a block and waits for one more byte ready
(`$F5CA`) before switching back to read, so the value on port A at the
end of a byte time is the one that fills it. Loading it at the start of
the byte time instead lost the last GCR byte of every block.

Switching between read and write resets the framing and the sync counter.

## The mechanism (`mechanics.rs`)

### Spindle motor

VIA2 PB2 switches it. The disk turns at full speed immediately: the
1541's 0.9 s spin-up wait is DOS software, not physics. When a job needs
the motor, the DOS switches it on (`$F97E`) and then waits 60 timer
ticks (`$48` = 60, decremented at `$F9D9`) before reading. After a job it
keeps the motor running for about 3.8 s (`$F98F`) before switching it
off. MAME models the motor the same way.

### Stepper and head

VIA2 PB0-1 drive the four phases of the stepper motor. A step of the
phase by +1 (mod 4) moves the head one half-track inward (towards higher
track numbers); −1 moves it outward. A jump by two is not a step and is
ignored. The DOS's seek routine (`$FA2E-$FA78`) shows the direction: with
"tracks to go" positive it does `INX` on the phase, negative `DEX`.

The head moves between physical half-track 1 (track 1, at the outer end
stop) and 83 (the last slot a G64 can hold). Stepping against the end stop
doesn't move the head; it is recorded as a "bump". That is the 1541's
famous head bang: when the DOS initialises a disk or retries a read error
it steps outward about 45 half-tracks blind, so the head knocks against
the stop. Every step is recorded with its drive cycle and whether it
bumped (`take_head_events`); the page plays them as sounds with the
original rhythm.

### Rotation

The head reads or writes the cell at `bit_pos` of the current half-track's
bit stream; the read/write electronics advance it one cell per bit clock,
wrapping at the end of the track. Because D64 tracks are sized to the zone's
capacity at 300 rpm, one revolution takes 200 ms. After a step the
position starts at 0 (on a real drive the landing point is arbitrary; the
DOS always waits for a sync mark).

### Write protect

VIA2 PB4 reads 1 when the disk is writable (the notch is open) and 0 when
it is protected or there is no disk. The DOS's write setup at `$FB00`
proceeds only when the bit is set. `Disk::write_protected` sets it.

### Two half-track numberings

The head counts physical steps from the outer stop: half-track 1 is track
1, and track t is at physical half-track `2t − 1`. `Disk` stores track t at
slot `2t` (1-based), as G64 files do. The mechanism adds one when it
addresses the disk. The page shows the head position as
`(half_track + 1) / 2`, so 18.5 is between tracks 18 and 19.

## Disks (`media/`)

A `Disk` is what the head sees: for each of 84 half-track slots, either
nothing or the raw GCR bytes of one revolution, plus the speed zone
recorded with it, and a write-protect flag. Reading and writing work on
this bit stream; nothing in the drive knows about sectors.

### GCR

Every 4 bits are written as 5, using the table shared with the earlier
Commodore IEEE-488 drives (`gcr::ENCODE`), so the stream never has more
than two 0-bits in a row (the read clock stays locked) or more than eight
1-bits (so data can't look like a sync mark). 4 bytes become 5.

A sector on disk is:

| Part | Raw bytes | On disk |
|---|---|---|
| sync | – | 5 × `$FF` (40 1-bits) |
| header block | `$08`, checksum (sector ^ track ^ id2 ^ id1), sector, track, id2, id1, `$0F`, `$0F` | 10 GCR bytes |
| gap 1 | – | 9 × `$55` |
| sync | – | 5 × `$FF` |
| data block | `$07`, 256 data bytes, checksum (XOR of the data), `$00`, `$00` | 325 GCR bytes |
| gap 2 | – | 4 × `$55` |

After the last sector the track is filled with `$55` up to the zone's
capacity (7,692 / 7,142 / 6,666 / 6,250 bytes).

### D64

`Disk::from_d64` takes a 35-track image of 174,848 bytes, or 175,531 with
the 683 error bytes (which are ignored). It reads the disk ID from the
BAM (track 18 sector 0, bytes `$A2`/`$A3`) and synthesizes every track as
above. 40- and 42-track images are rejected.

`Disk::to_d64` goes back: it scans each track at the bit level (sectors
written by the drive can start at any bit offset), treating the track as a
loop, finds each sync mark of ten or more 1-bits, decodes a header, finds
the data block's sync within a short window after it, and checks both
checksums. A sector that can't be read comes out as 256 zero bytes.

### G64

`Disk::from_g64` reads the `GCR-1541` format (Peter Schepers' G64.TXT):
signature, version, number of half-tracks, maximum track size, a table of
track offsets, a table of speed zones, and each track as a length and its
raw bytes. Every half-track is kept as it is, so copy protections that
depend on the raw stream (odd sync lengths, half-tracks, non-standard
gaps) are seen by the DOS or a custom loader as on a real disk.
`Disk::to_g64` writes the same format.

The page keeps the disk as a D64 when it takes it back from the drive
(at power-off, eject or download), so a G64's raw details last only while
the machine is on.

## Outputs for a front end

| Method | Gives |
|---|---|
| `take_led_duty()` | the fraction of cycles the red activity LED was lit since the last call (it can flicker faster than a video frame) |
| `motor_on()` | the spindle motor |
| `current_half_track()` | the head position |
| `take_head_events()` | each step since the last call: its drive cycle, and whether it hit the stop |
| `disk()`, `eject_disk()` | the disk, with everything written to it |

## How a `LOAD` goes

For orientation, what happens on `LOAD"$",8` with these parts:

1. The KERNAL sets CIA2 PA3: ATN is pulled low. The drive's XOR gate pulls
   DATA low within a cycle: the KERNAL sees a device.
2. ATN's rising edge on VIA1 CA1 interrupts the drive's 6502 (once it
   allows interrupts). The DOS sets ATNA and receives the LISTEN, the
   secondary address and the file name byte by byte: the C64 releases
   CLOCK, the drive releases DATA, eight bits are clocked with CLOCK and
   sampled on DATA, and the drive acknowledges each byte by pulling DATA.
3. The DOS queues a read job. Its timer interrupt starts the motor and
   waits 0.9 s, reads a header to learn where the head is, steps to track
   18 (ticking the stepper and moving the head), and waits for the sync
   and header of the wanted sector, then its data block, through byte
   ready and VIA2 port A.
4. TALK: the roles turn round and the drive sends the bytes to the C64.
5. The KERNAL puts them in memory; `LIST` shows the directory.

The emulator does every one of those steps with the real KERNAL and DOS,
which is why fast loaders, which replace steps 2 and 4 with their own
protocols, and demos with custom drive code work too.

## Not modelled

- Motor speed variation and spin-up: the disk turns at its nominal speed
  from the moment the motor is switched on.
- Weak or random bits: an empty half-track reads as zeros.
- Writing to a half-track that has no data at all (a `Disk::blank()`):
  the head writes only where the disk has a track buffer, which every D64
  and the page's `empty.d64` have.
- The 1541-II, the 1571 and parallel cables.
