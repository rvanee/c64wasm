# Test strategy

## Principles

1. **Test against something outside the code.** An emulator that is only
   compared with itself drifts. Every behaviour that matters is checked
   against an outside reference: measurements of real chips (Tom Harte's
   single-step tests), VICE, the real KERNAL and DOS ROMs running on the
   emulated hardware, or screenshots of real software.
2. **Test each chip on its own, then the machine.** Chip tests drive one
   chip directly with no CPU running, so a failure points at that chip.
   Machine tests run the real ROMs and check what a user would see.
3. **Run everything in CI without committing ROMs.** Tests that need
   Commodore ROMs look in `roms/` and skip themselves when the ROMs aren't
   there. CI rebuilds the ROMs from public listings for each run, so the
   full suite runs there too.
4. **A refactor must not change behaviour.** For changes that shouldn't
   change what the machine does, the outputs of whole demos are compared
   byte for byte before and after.

## Running the tests

```sh
node web/tools/rebuild-roms.mjs      # once: rebuild the ROMs into roms/ (Node 20+)
cargo test --release --workspace     # Rust: unit and integration tests
cd web && node --test                # JavaScript: ROM rebuilding
```

Always use `--release`: the disk tests emulate minutes of machine time
(formatting a disk takes about 79 emulated seconds, as on a real 1541).

## What is tested where

### CPU

| Test | Reference | Needs ROMs |
|---|---|---|
| `src/bin/tomharte.rs` (harness, not part of `cargo test`) | SingleStepTests/65x02 `6502/v1`: 10,000 cases per opcode, all 256 opcodes, with registers, memory and every bus cycle | no |
| `src/cpu/tests.rs` | known 6502 facts: flags, page-crossing cycles, the `JMP ($xxFF)` bug, JAM, the SO pin setting V mid-instruction | no |
| `tests/cia_timing.rs` (interrupt part) | VICE: when an IRQ or NMI is taken relative to the instruction stream | no |

The single-step harness needs the test vectors, which are large and not in
the repository:

```sh
git clone --depth 1 https://github.com/SingleStepTests/65x02
cargo run --release --features harness --bin tomharte -- 65x02/6502/v1
cargo run --release --features harness --bin tomharte -- 65x02/6502/v1 9e --verbose 3
```

It prints, per opcode, how many cases passed, and for failures the first
differences (registers, memory, or the cycle where the bus trace differs).
All 2,560,000 cases pass (October 2026). Run it after any change in
`cpu/`.

### Chip timing against VICE

`tests/cia_timing.rs` runs two small machine-code programs that bank the
ROMs out and install their own vectors, so they need no Commodore ROMs:

- `tests/data/cia_timing.prg`: reads timer A 0-3 NOPs after starting it,
  force-loads a running timer and reads it back, and counts how many
  2-cycle `INX` instructions run between starting a one-shot timer of 8-15
  cycles and its interrupt, for CIA1 (IRQ) and CIA2 (NMI).
- `tests/data/raster_irq.prg`: takes a raster interrupt on line `$80` from
  a `JMP *` loop with the screen blanked; the handler must start in cycle
  9, 10 or 11 of the line.

The expected values were read from VICE x64sc 3.7.1's monitor running the
same programs. The programs are generated by the Python scripts next to
them (`make_cia_timing_prg.py`, `make_raster_irq_prg.py`), so they can be
changed and re-measured.

### VIC-II

`tests/sprites.rs`, `tests/ecm.rs`, `tests/crab_collision.rs` and
`tests/ntsc.rs` build a C64 with all-zero ROMs, set up registers and memory
directly, clock the board without running the CPU (`Board::tick`), and
then read the framebuffer and the collision registers. Pixels are compared
with each other ("this pixel has the sprite's colour, that one the
background's"), not with RGB constants, so the tests don't depend on the
palette; only the invalid ECM modes are checked for pure black.

| File | Covers |
|---|---|
| `sprites.rs` | bounding box, X/Y expansion, multicolour, priority between sprites, sprite-sprite and sprite-background collision with MDP, the border covering sprites, sprite crunch (an expanded sprite lasts more than 41 lines) |
| `ecm.rs` | extended colour mode's four backgrounds; the invalid ECM modes are black |
| `crab_collision.rs` | collisions with the irregular sprite of a real BASIC program (`SpriteCollision.bas`), against text-mode foreground |
| `ntsc.rs` | framebuffer size and clock per standard; a frame wraps cleanly |

Demos are the hardest VIC-II test. The Performers demo's face scene
(sprite crunch) was checked against a VICE screenshot.

### SID

`src/sid/mod.rs` has unit tests: sawtooth period matches the frequency
register, TEST holds the oscillator, hard sync, noise is not silent and
changes, OSC3/ENV3 are readable, attack timing (255 rate periods), the
ADSR delay bug, a low-pass filter attenuating a high tone, and that volume
writes are audible on a 6581 (digis). `examples/sid_wav.rs` records a
BASIC program's sound to a WAV file for listening.

### 1541 and disks

| Test | Covers | Needs ROMs |
|---|---|---|
| `src/media/gcr.rs` | GCR table (no duplicates, every nibble round-trips, invalid codes rejected), header and data block round-trips and checksums, sync marks can't be GCR data | no |
| `src/media/d64.rs`, `g64.rs` | D64 sizes and zone table, D64 → GCR → D64, disk ID in every header, G64 parsing and round-trip | no |
| `src/drive1541/...` | VIA mirroring, RAM mirroring, reset vector, device numbers, ATN-acknowledge truth table, stepper and end stop, read/write channel (sync detection, byte framing after a sync, written bytes read back, a value left on port A rewritten every byte time) | no |
| `src/via/mod.rs` | DDR, T1 one-shot and free-run with PB7, IER summary bit, CA1/CA2 edges and clearing, port A latching, manual CA2/CB2 outputs | no |
| `tests/drive1541_boot.rs` | the real DOS boots and programs both VIAs as the disassembly says (VIA1 DDRB = `$1A`, VIA2 DDRB = `$6F`) | 1541 |
| `tests/drive1541_bus_integration.rs` | C64 and drive run side by side; ATN from CIA2 reaches VIA1 PB7. Works with either DOS version: 901229-05 sets up VIA1 early, 901229-01 after its RAM/ROM test | all |
| `tests/disk_basic_roundtrip.rs` | see below | all |

`disk_basic_roundtrip.rs` does what a user does at the keyboard, through
the real KERNAL, the real DOS and the emulated serial bus and disk:

- `LOAD"$",8` and `LIST`; `LOAD"HELLO",8,1` and `RUN`;
- the demo programs on the test disk run;
- the empty disk is formatted and empty (664 blocks free);
- format a disk with `OPEN15,8,15,"N:..."`, type the Space Shuttle
  listing, `SAVE`, `NEW`, `LOAD`, and compare the tokenized program byte
  for byte; then export the disk as a D64 and load it again on a freshly
  booted machine, so the bytes really went through the drive's GCR write
  path and back;
- save a program from a relocated BASIC start (`$4001`) and load it back
  with `,8,1` (absolute) and, on a fresh machine, with `,8` (relocated);
- the offline BASIC tokenizer (`tools::basic`, used to build the test
  disks) produces the same bytes as the real screen editor.

Text is put in the KERNAL's keyboard buffer for speed; the keyboard matrix
itself is tested in `tests/boot.rs`.

### Machine

`tests/boot.rs`: the KERNAL and BASIC boot to `READY.` on PAL and NTSC
(the banner's free-memory count checks RAM size and banking), and typing
through the CIA1 keyboard matrix works. Needs the C64 ROMs.

### Web page

`web/test/roms.test.mjs` (`node --test` in `web/`):

- CRC32 of the standard check string; solving three missing bytes from a
  CRC;
- every listing shape the parser reads (disassembly, VICE monitor,
  assembler with line numbers, label column, `.BY`/`.WD`, xxd, hexdump -C,
  a comment after the bytes), elided ranges, HTML tables;
- a font drawn as text;
- gaps are reported;
- with the real ROMs: a 1541 listing without its unused first page and
  with a mistyped address is repaired to the exact ROM; a KERNAL listing
  with a byte left out is repaired from the CRC.

`.github/workflows/ci.yml` also runs `node --check` on every JavaScript
file of the page.

## ROMs in CI

The ROMs can't be in the repository, so CI rebuilds them for each run:
`node web/tools/rebuild-roms.mjs` downloads the same public listings the
page uses (see [web.md](web.md#getting-a-rom-sourcesjs)), rebuilds each
ROM and checks it against the real chip's CRC32, and writes them to
`roms/`. They are never committed, cached or uploaded as artifacts. The
run's summary shows which ROMs were rebuilt. If a site is down, that ROM
is missing for the run: a warning appears and the tests that need it skip
themselves.

The rebuilt ROMs are BASIC 901226-01, KERNAL 901227-03, character ROM
901225-01 and the 1541's original 325302-01 + 901229-01. Tests must work
with any known version of a ROM (the drive integration test once assumed
901229-05's timing).

## CI pipeline

On every push and pull request (`.github/workflows/ci.yml`):

1. `cargo fmt --all --check`;
2. `cargo clippy --release --workspace --all-targets -- -D warnings`
   (the current stable Rust, so a new release can bring new lints);
3. rebuild the ROMs;
4. `cargo test --release --workspace`;
5. `node --test` in `web/`;
6. build the wasm module, `node --check` the JavaScript, and package the
   page.

Pushes to `main` publish the page; tags `v*` attach it to a release.

## Regression checks against real software

Some behaviour is only visible in real programs: demos, games, fast
loaders. The examples in `crates/c64-core/examples/` make those checks
repeatable:

| Tool | Does |
|---|---|
| `demo_probe <disk> <seconds> <out> [command]...` | boots with a disk, types commands (e.g. `LOAD"*",8,1`, `RUN`), runs, reports every second what both CPUs are doing (busiest code areas, serial bus, head, motor) and saves raw RGBA frames and both RAMs; `NTSC=1`, `EVERY=n` |
| `vic_trace <disk> <seconds> <out>` | loads and runs a disk, then traces one frame: sprite registers and units per line, or the raster position at given PCs (`PCS=`), or every change of the main VIC-II registers (`WRITES=1`) |
| `run_prg <file.prg> <start> <cycles> <dump-from> <length>` | runs a PRG from a given address and dumps RAM; `PCS=` prints raster positions at given addresses |
| `sid_wav <program.bas> <out.wav> <seconds> [8580]` | types a BASIC program, runs it, records the SID |

**Before/after comparison.** For a change that shouldn't change behaviour
(a refactor), run `demo_probe` on the same disks before and after and
compare the hashes of the saved frames and RAM dumps: they must be
identical. When a change is meant to alter output (an emulation fix), the
frames that change are compared with VICE screenshots of the same moment,
and the new hashes become the baseline.

## Manual checks

Before a release, in a private browser window (no stored ROMs):
the first-run dialog, finding the ROMs automatically, `LOAD"$",8` from the
test disk, the 1541 display zoom, the 2002's door and knobs, the
monitor's power switch, the flat panel, and adding a ROM by URL. The steps
are in [publishing.md](publishing.md#1-check-it-locally).

## Adding a test

- A chip behaviour: a unit test in the chip's module, or an integration
  test with blank ROMs that drives the chip through `Board::tick`.
- A timing behaviour: a small PRG generated by a script, its expected
  values measured in VICE, and a test like `cia_timing.rs`.
- Something that needs the ROMs: get them with `common::roms(name,
  need_1541)` and return early when it gives `None`.
- A bug found in real software: reduce it to the smallest program that
  shows it, and keep that program as the test.
